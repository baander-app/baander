# Consolidate Doctrine migrations into one initial schema

## Goal and agreed scope

Replace all 53 Doctrine migrations with one migration creating the current
80-table application schema. Preserve constraints, indexes, extensions and
required seed data. The supplied user plan is the source of this scope.

The only intended schema changes are replacing the two legacy `BIGSERIAL` keys
in `domain_event_outbox` and `domain_event_outbox_delivery` with
`BIGINT GENERATED BY DEFAULT AS IDENTITY`.

Reset only the local `baander` database in `baander-postgres`, after verification.
Other non-empty targets require their owner's explicit approval and a separate
manual reset. There is no automatic deletion, overwrite option or destructive
confirmation prompt in the migration.

## Implementation units

### Capture and replace the schema

Capture the existing chain's final catalog and seed data in disposable PostgreSQL
infrastructure before removing historical files. Create one self-contained,
transactional `migrations/Version20261017000000.php` with explicit final SQL.
Preserve all seven extensions, five PGroonga indexes and their options, nine
trigram indexes, generated columns, foreign keys, checks, partial/expression
indexes and migration-owned runtime tables. Preserve public-ID constraints,
timestamp precision and JSON versus JSONB distinctions.

Seed exactly the OAuth purge schedule at 03:30 UTC and recommendation schedule at
04:00 UTC, retaining configuration and fixed internal IDs. Generate independent
public IDs and calculate scheduling timestamps from one clock sample. Remove
obsolete backfills, repairs, intermediate changes and the retired health-check
schedule. Make `down()` explicitly irreversible. Remove the legacy comparator
and its wiring; future migrations use normal timestamp ordering.

### Guard initialization and migrate fixtures

Before Doctrine executes the initial migration, verify the target is empty.
Existing user tables, including tables without rows, views, sequences, types and
routines make a target non-empty. Exclude system objects, extension-owned objects
and an empty Doctrine metadata table. Refuse before application DDL, identify the
database without credentials, and explain the target-specific approval and
separate manual reset requirement. Non-interactive execution and Doctrine's
ordinary confirmation cannot bypass this check.

Retain the unknown-history guard, replacing repair guidance with reset guidance.
Apply the emptiness check only while the initial migration is pending; migrated
databases must support no-op runs and future migrations.

Replace historical replay in integration tests and runtime fixtures with a shared
final-schema bootstrap. Isolated-schema fixtures verify their own schema is empty
and reuse provisioned extensions. Remove only obsolete upgrade/downgrade tests;
retain constraint, persistence, outbox rollback, scheduler and concurrency coverage.

### Verify, document and reset the authorized target

Compare old and new catalogs, permitting only the two identity changes and
irrelevant catalog identifiers. Validate all seed semantics, including generated
fields. Verify one discovered/executed migration, identity allocation and an
unchanged second migration run. Test refusal for empty tables, populated data,
unrelated objects and old history, preserving their objects and rows under
non-interactive execution. Verify extensions-only initialization, continued use
after migration and irreversible downgrade without mutation.

Run authoritative backend suites, static gates, runner/isolation regressions and
affected runtime drills. Record actual counts, timings and justified reductions
from removed historical tests in `ROADMAP.md`.

Update installation, testing and upgrade guidance, obsolete migration references
and PostgreSQL skill references. Document fresh installation and explicitly
approved manual reset without automatic compatibility paths. Use existing
`CONCEPTS.md` terminology; add entries only for new concepts.

Once verification passes, preserve database creation settings and running-service
state, stop active writers, recreate only `baander` in `baander-postgres`, migrate
twice, then restore services. Leave `baander_test`, other databases, PostgreSQL
volumes, Redis, registry storage and media untouched. Do not use `drop-migrate`.

## Delivery and acceptance

Work on `plan/consolidate-doctrine-migrations`. Review this plan before code
changes. Apply simplification and independent code review, check documentation
prose and commit locally. A push or merge requires a separate request.

Acceptance requires catalog equivalence except the approved identities, proven
non-empty refusal without mutation, passing affected gates, the authorized local
reset with service restoration, and verification evidence recorded in the roadmap.
